# LX allocation: what the choice is worth, and whether a cost model can improve it

**Conclusion.** The choice is worth up to 2.74× measured. The compiler's CP-SAT solver
already makes it near-optimally (36 of 37 contested bundles). The *default* solver does not
(21 of 37, losing up to 18.2%), and neither do `firstfit`/`bestfit`. So the actionable result
is a one-line config change, not a cost model. A cost model beats CP-SAT only in a corner
case, and cannot be trusted to rank anything until a monotonicity bug is fixed.

All numbers are generated by `research/lx_choice.py` against the recovered measurement
database (commit `3f57eb5`, 2828 records). No hardware was used; the commands that regenerate
each result are shown inline. Three claims in earlier drafts of this document were wrong and
are listed in §8.

---

## 1. What LX residency is worth (measured)

56 configurations were measured twice, once with `LX_PLANNING=0` and once with `=1`:

| op | shape | LX off / LX on |
|---|---|---:|
| add3 | 2048×1024 | 1.59× |
| add4 | 2048×1024 | 2.11× |
| add5 | 2048×1024 | 2.60× |
| add6 | 2048×1024 | **2.74×** |
| everything else | — | ~1.00× |

The effect grows with the length of the fused chain. `add{N}_sep` — the same arithmetic split
into separate compiled kernels — sits at 1.01×, which identifies the mechanism: separate
kernels cannot keep an intermediate on chip, so there is nothing for LX to hold.

## 2. Capacity binds, and the boundary is visible in measurement

The same op at three widths, against the compiler's budget of **1587 KB/core**
(`_lx_planning_size()`, `scratchpad/allocator.py:838-855`):

| shape | per-core footprint | fits? | recorded residency | measured benefit |
|---|---:|---|---|---:|
| 2048×1024 | 128 KB | yes | `lx` | 1.59–2.74× |
| 2048×4096 | 512 KB | yes | `lx` | 1.58–2.60× |
| 2048×16384 | 2048 KB | **no** | `hbm` | 1.00× |

At 16384 columns a single intermediate exceeds the budget, the allocator spills it, and
`LX_PLANNING=1` becomes indistinguishable from `=0`.

## 3. The harness, and why its output can be trusted

To rank allocations on programs we cannot measure, `lx_choice.py` flips `ArgTraffic.mem`
between `lx` and `hbm` and re-runs `predict_ops`. `--validate` checks that this substitutes
for an actual recompile, against the 56 measured pairs:

```
direction agrees on 15/15
where LX matters (>1.2x, n=8): median magnitude error 7%
```

Two things had to be right for that, and each was found by getting a wrong answer first:

- **Buffer identity.** The extractor names the same buffer `op3` where it is produced and
  `buf3` where it is consumed. Matching on raw names found *no* intermediates at all, so a
  six-operand add chain appeared to have nothing to allocate.
- **Peak liveness, not sum.** Chain intermediates die as fast as they are born, so `add6`
  holds about two tiles at once, not four. Summing rejected an allocation the compiler had
  actually made, turning a measured 2.60× into a predicted 1.80×.

The residual is a 6–13% under-prediction growing with chain depth, consistent with the
read-after-write cost that `cost_model.py:1237` documents as deliberately unmodelled.

```sh
python3 research/lx_choice.py --validate
```

## 4. The choice is genuinely non-trivial

A bundle is *contested* when capacity binds and the feasible choices differ in predicted
time. **37** such bundles exist in the recorded data, spreads up to **1.85×**.

The clearest is a row-tiled softmax, `[16384, 2048]`:

| buffer | producer | per-core | consumers | worth keeping alone |
|---|---|---:|---:|---:|
| b0 | `amax` | 16 KB | 1 | 93 µs |
| b1 | `sub` | 512 KB | 1 | 425 µs |
| b2 | `exp` | 512 KB | **2** | **732 µs** |
| b3 | `sum_1` | 16 KB | 1 | 127 µs |

`b1` and `b2` are **byte-identical** and `b2` is worth 1.7× more, because `exp`'s output
feeds both `sum_1` and `div` while `sub`'s feeds only `exp`. Size alone cannot separate them.

```sh
python3 research/lx_choice.py --contested
```

## 5. Which policies get it right

Each policy's pick measured against the time-optimal feasible allocation, over all 37:

> **Confirmed on a second, much larger corpus.** Flash attention has 20 movable buffers
> against softmax's four, and exhaustive search there gives the same verdict: CP-SAT is
> exactly time-optimal, while the default `greedy` is 20–28 % off and `bestfit` 20–22 %.
> See `research/flash_lx_findings.md`. (The scan below missed those bundles entirely,
> because the enumerator silently skips anything above 16 buffers.)

| policy | time-optimal on | worst regret |
|---|---:|---:|
| `cpsat` — minimises `(reads + 1) · size` | **36/37** | +0.6% |
| largest-first | 36/37 | +0.6% |
| `firstfit` / `bestfit` — `(lifetime − discount)/uses` ordering | 21/37 | +18.2% |
| **`greedy` — the DEFAULT — program order** | **21/37** | **+18.2%** |

**`greedy` is the worst option measured and it is what ships.** It walks the program in
order, so it reaches `b1` before `b2`, takes it, and has no room left for the buffer worth
1.7× more. Its mistake is identical in all 16 failures: `{b0,b1,b3}` where `{b0,b2,b3}` was
available.

**`firstfit`/`bestfit` are not the fix**, which matters because they are the obvious thing to
try. Their ordering scores `b1` at 2/2.5 = 0.80 against `b2`'s 3/3.5 = 0.86, so they take
`b1` first too. Only CP-SAT's objective separates the two buffers, because `read_count`
distinguishes them where size does not.

```sh
python3 research/lx_choice.py --policies
```

## 6. When a cost model could beat CP-SAT, and why it is a corner case

Both rank the same quantity. CP-SAT counts the traffic a spill adds, `(consumers + 1) × size`.
The cost model divides that same traffic by the rate it moves at. **So when every candidate
moves at the same bandwidth the two rank identically** — dividing all scores by one constant
cannot reorder them. Every op in the recorded contested bundles runs at the default
150 GB/s, which is why CP-SAT is not approximately right there but exactly right.

They can disagree only when rates differ, and the model's rates span **3.75×**:

| access pattern | GB/s |
|---|---:|
| default | 150 |
| broadcast, `restickify`, `reduce_outer` | 113–118 |
| `cat1` floor / `transpose_outer` floor | 90 / 83 |
| **`cat0` / `stick_scatter` floor** | **44** |
| **`transpose_outer` after its M penalty** | **40** |

The flat overrides (1.33×) rarely overturn a traffic ratio. The shape-dependent ones can:
`cat0` is `clamp(144 − 9.6·log2(C/64) − 2.4·log2(R), 44, 150)`, which is 89 GB/s at
`[2048,512]` and hits its 44 GB/s floor at `[4096,12800]` — the Granite MLP shape.

Marking one op of a real bundle with each pattern in turn and re-ranking, CP-SAT's regret
reaches **36.6%** when a `stick_scatter` buffer is in contention, and the flat patterns never
cost more than 1.3%. In one case the time-optimal set is `{b0,b1}` while CP-SAT picks
`{b0,b2,b3}` — a different choice, not a smaller one.

**This is real but narrow.** It requires a slow-transport buffer to be an LX candidate, and
it was shown by perturbing recorded features, not on any real program. Such candidates are
reachable — a materialised transpose lowers to `clone`, which is on the eligibility
allowlist, and carries `stick_scatter` 46 times in the corpus — but no measured workload has
been shown to hit it.

## 7. A blocker: the model is not monotone in residency

Moving a buffer from HBM into LX removes traffic and adds nothing, so predicted time must
never rise. On **14/37** contested bundles it does, by up to 2.4%.

The cause is a branch discontinuity. Spilling a small broadcast operand makes its consumer a
*broadcast op*, which flips the whole bundle from `bw_peak + α·min(R,W)` onto the per-op
effective-bandwidth formula — and that branch folds turnaround into the rate instead of
charging it. On one bundle the raw memory term rises 640.0 → 650.0 µs while the prediction
*falls* 640.0 → 636.3 µs.

A ranker cannot be more trustworthy than the ordering it ranks by, so this blocks any
model-driven policy. It is also a bug in its own right: two programs differing only in
whether an operand is broadcast are priced by different formulas with a step between them.

```sh
python3 research/lx_choice.py --monotonicity
```

## 8. Claims in earlier drafts that were wrong

Recorded because the reasoning matters more than the conclusions.

1. **"The bandwidth envelope is 1.33×, so a cost model can essentially never beat the byte
   proxy."** The envelope was computed from the two flat constants and omitted every
   shape-dependent transport, which reach 40 GB/s. It is 3.75×, and the conclusion reverses.
2. **"`lx_spill_cap_bytes` (512 KB) is a 3.1× error against the real 1587 KB budget."**
   Setting it to the true budget makes softmax *worse* (RMS 21.1 → 22.2%). It is a fitted
   derate knee, not a capacity. The fix is to rename it, not retune it.
3. **"`bestfit` and `cpsat` both reach 36/37, so switch the default to `bestfit`."**
   `bestfit` was never measured — only CP-SAT and largest-first were. Its actual ordering
   measures 21/37, identical to `greedy`.

Each was caught by testing the claim rather than reasoning from it.

## 9. What follows

1. **Change the default `layout_solver` from `greedy` to `cpsat`** — 21/37 → 36/37, one
   config line, no cost model. `bestfit` is not a substitute (§8.3).
2. **Warn when a buffer is denied LX for want of room.** Today the compiler's most
   consequential allocation event is invisible above DEBUG.
3. **Rename `lx_spill_cap_bytes`**, which reads as a capacity and is not one.
4. **Fix the monotonicity break** (§7) before building anything that ranks allocations.
5. **Do not build a cost-model LX policy** on the strength of §6 alone. See
   `research/lx_policy.md` §6 for where the larger opportunities are — tile size, which has
   no incumbent at all, and layout conversion, where IBM's own published numbers are 2.3×.
